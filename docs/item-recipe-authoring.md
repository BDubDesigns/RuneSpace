# Item & recipe authoring — quick checklist

Use this after reading [AGENTS.md](../AGENTS.md) and the issue's approved scope. Follow the canonical values in [`game/config/balance.ts`](../game/config/balance.ts), not values copied into a guide. A new item, a new recipe, and a new way to obtain an existing item are **different changes**.

## Pick the changes you actually need

| Change | Required authoring | Conditional work |
| --- | --- | --- |
| New inventory item | Stable `ITEM_IDS` entry; balance item **schema and defaults**; Wiki category; presentation | Approved art/derivative, equipment or usable-item fields, acquisition path |
| Fabrication/Refining recipe using existing items | Stable `ACTION_IDS` entry; recipe **schema and defaults** in balance | Tinkering target, new station/location or progression rule **only if approved** |
| Both | Both rows above | No extra registry just because they ship together |
| New source for an existing item | Author the actual source (Mining, merchant, Mission reward, etc.) | Source action/location, eligibility, inventory or economy checks specific to that source; no duplicate item |

### Item checklist

- [ ] **Required:** Add an immutable item ID to [`game/config/foundations.ts`](../game/config/foundations.ts). IDs are durable identities; don't change an existing ID merely to change its displayed name.
- [ ] **Required:** In [`game/config/balance.ts`](../game/config/balance.ts), add the item to **both** `GameBalanceSchema.items` (typed/validated shape) and `DEFAULT_GAME_BALANCE.items` (authored values). Choose stackable (`stackLimit`) or unique, `massGrams`, and only relevant `equipment`, charge, capacity, or special use fields. `getItemDefinition()` and `inventoryItemDefinitions()` then expose the shipped item; an `ITEM_IDS` constant alone does not ship it.
- [ ] **Required:** Classify the shipped item **once** in [`game/content/item-categories.ts`](../game/content/item-categories.ts). `validateItemCategories()` enforces complete, non-extra Wiki coverage.
- [ ] **Required:** Register singular/plural naming as needed, accessible art facts, text fallback, description if authored, and runtime `artworkSrc` if art exists in [`game/content/item-presentation.ts`](../game/content/item-presentation.ts). Do not put mass, stack limits, or independently repeated balance values into presentation prose.
- [ ] **Conditional (approved art):** Preserve the owner's master in [`assets/item-art/`](../assets/item-art/) and ship its optimized derivative in [`public/item-art/`](../public/item-art/); use its real runtime path. Inspect at inventory size. Follow the [art cookbook](art-cookbook.md). **Never invent, regenerate, or replace unapproved art** to complete this list; surface missing approval instead.
- [ ] **Conditional (how acquired/used):** Add only the actual source/consumer: e.g. `game/config/balance.ts` Mining sources (plus appropriate `game/content/locations.ts` action), [merchants](../game/content/merchants.ts), [missions](../game/content/missions.ts), or [scavenge](../game/content/scavenge.ts). An item may have no recipe; adding a recipe already creates its recipe source. Follow [Mission](missions.md) and [NPC/conversation](npc-conversations.md) guides and [NPC canon rules](npc-canon.md) for cross-domain work, rather than inventing their content here.

### Fabrication / Refining recipe checklist

- [ ] **Required:** Assign **one durable recipe action ID** in [`game/config/foundations.ts`](../game/config/foundations.ts) `ACTION_IDS`, including when outputting an existing item. Don't reuse the output item's ID as the action.
- [ ] **Required:** Add the recipe under `GameBalanceSchema.fabrication.recipes` or `GameBalanceSchema.refining.recipes` **and** its matching `DEFAULT_GAME_BALANCE` entry in [`game/config/balance.ts`](../game/config/balance.ts). Match existing typed recipes: `actionId`, `outputItemId`, `inputs`, `outputQuantity`, `minimumLevel`, duration and XP; Fabrication has `baseXp`, while Refining has its own success curve / deterministic or failure branch. Reuse balance values and semantics; don't invent mechanics. `fabricationRecipes()` and `refiningRecipes()` expose the registry in authored order.
- [ ] **Check gates, don't duplicate them:** Personal Fabrication/Refining skill `minimumLevel` is separate from station discovery/access and current location. The Refining console is hosted via `ACTION_IDS.refining` in [`game/content/locations.ts`](../game/content/locations.ts), **not** by adding each recipe ID to `availableActionIds`. Rusk Recovery's Fabrication Station and its Mission-acceptance unlock live in [`game/content/rusk-recovery.ts`](../game/content/rusk-recovery.ts). Change location/station authorization only when the issue explicitly adds one.
- [ ] **Conditional:** [`balance.tinkering.targets`](../game/config/balance.ts) separately opts eligible Fabrication outputs into Tinkering (with its own action ID); not every Fabrication recipe belongs there. Manual Override is shared Fabrication behavior, not a per-recipe registration. Check run selection, ingredient/carry limits, and the correct outcomes (success, failure, XP, ticks) against the [gameplay rules](gameplay-foundations.md).
- [ ] **Safety boundary:** [`game/domain/fabrication.ts`](../game/domain/fabrication.ts), [`game/domain/refining.ts`](../game/domain/refining.ts), [`game/domain/recipe-unlocks.ts`](../game/domain/recipe-unlocks.ts), and [Fabrication](../server/fabrication-commands.ts) / [Refining](../server/refining-commands.ts) server commands own selection, access, bounded runs, settlement and unlock behavior. **Read to verify; do not normally edit** for a declarative recipe. Keep rules server-authoritative; do not create a React recipe catalog.
- [ ] **Refining failure caution:** Check `fixed_outputs` vs `one_input_returned` / `none`, output and returned-input capacity after consumption, Auto-discard Slag, and retry/idempotence boundaries. `partitionFailureAwards()` in [`game/domain/refining.ts`](../game/domain/refining.ts) already distinguishes returned inputs from made byproducts by recipe inputs; don't recreate that rule in UI or Wiki copy.

### Derived automatically — do not hand-register

- [`game/domain/item-sources.ts`](../game/domain/item-sources.ts) projects **character-aware repeatable acquisition** from the recipe, Mining, merchant, location, Scavenge and fixed-claim owners. It intentionally does **not** list one-time Mission rewards as repeatable sources.
- [`game/domain/item-reference.ts`](../game/domain/item-reference.ts) projects the **public, spoiler-complete** item facts, including authored recipes, repeatable sources, Mission rewards and Refining failure byproducts. [`features/public-site/public-item-wiki.ts`](../features/public-site/public-item-wiki.ts) builds `/wiki/items` from `inventoryItemDefinitions()`, not hand-authored articles. See [public Wiki policy](public-wiki.md); edit editorial Wiki pages only when existing player-facing facts materially change.
- [`game/domain/recipe-unlocks.ts`](../game/domain/recipe-unlocks.ts) derives level-crossing notices from `fabricationRecipes()` / `refiningRecipes()` and `minimumLevel`: no separate unlock list.

### Review & proportional validation

- [ ] Check new item presentation/art, unique vs stack semantics, slot/mass capacity, storage/trading and equipment/charges where applicable. Look at `tests/unit/item-definition.test.ts`, `item-presentation.test.ts`, `item-transferability.test.ts`, plus source- or feature-specific tests.
- [ ] Check Wiki category/source/recipe derivation and any merchant or Mission source interactions: `tests/unit/public-item-wiki.test.ts`, `item-sources.test.ts` and relevant feature tests.
- [ ] Check recipe unlock notice order, skill/station gating, bounded runs, preflight capacity, both settlement outcomes, returned inputs and Auto-discard; include concurrency/idempotence when that boundary is affected. Start with `tests/unit/recipe-unlocks.test.ts`, `deep-jag.test.ts`, `fabrication.test.ts`, `refining-domain.test.ts`, `tests/integration/recipe-unlock-notices.test.ts` and focused `tests/e2e/fabrication-advanced.spec.ts` when applicable.
- [ ] Inspect tests asserting **exact authored registry membership/order/count** and update their intentional expectations for new entries (e.g. recipe unlocks and Deep Jag). An unrelated hard-coded list size may be a brittle test, not a new gameplay rule: diagnose before altering it; do not blanket-replace counts or refactor unrelated tests in a content PR.
- [ ] Follow [`docs/game-rules.md`](game-rules.md), [gameplay foundations](gameplay-foundations.md), [public Wiki](public-wiki.md) and [public Updates](public-updates.md) **only when behavior or documented player facts warrant it**, per [AGENTS.md](../AGENTS.md). Run focused tests, `pnpm typecheck` and `pnpm format:check` (and other relevant cheap checks) locally when available, then let PR CI prove the full suite; see [testing strategy](testing-strategy.md) and [development workflow](development-workflow.md). Report anything unexecuted.

### Locator example: Fuel Manufacturing (#343 / [PR #346](https://github.com/BDubDesigns/RuneSpace/pull/346))

The empty/full canisters appear in `ITEM_IDS`, both balance item schema/defaults, presentation and categories; approved PNG masters in `assets/item-art/` produce runtime WebP derivatives. Their two recipe `ACTION_IDS` and Fabrication/Refining schema/defaults are in `balance.ts`. The Refining recipe uses the existing console and `fixed_outputs` for the Oil Shale and empty shell returned on failure; shared `partitionFailureAwards()` handles presentation/reference classification and Auto-discard safety. The empty-shell Fabrication recipe **does not** opt into Tinkering. The item Wiki and unlock notices derive from the registries, not extra registrations. Use this to **find owners**, not to copy fuel-specific rules into the next recipe.
